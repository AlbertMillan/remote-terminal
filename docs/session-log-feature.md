# Project Session Log (`SESSION-LOG.md`)

A modular feature that captures *what happened* in each Claude Code session and
writes it to a per-project `SESSION-LOG.md`, so an unfinished project can be
understood at a glance — both by a human and by a future Claude session.

Status: **design / plan** (not yet implemented). Off by default.

---

## 1. Goal

When a Claude session inside a project ends, automatically append a short,
structured entry to that project's `SESSION-LOG.md` describing:

- the features added/modified (grounded in the real git diff, not just intent),
- which objectives from the project's plan/design docs were completed,
- what's still open and any blockers.

Entries are generated by a **headless `claude -p` run** (billed against the
Pro/Max subscription, *not* the pay-per-token API). A cross-project dashboard
reads these files to show the state of every project in one place.

---

## 2. Why a markdown file (not a DB table)

- A dedicated `SESSION-LOG.md` does **not** pollute future session context. A
  markdown file only enters a session's context if it is `CLAUDE.md`, is
  `@import`-ed into one, or Claude reads it deliberately. So it costs nothing by
  default and *helps* when you want the history.
- No extra schema/serialization complexity. The file is the source of truth.
- It is committable, diffable, and human-readable — a natural project changelog.

The only structured element is a machine-readable HTML comment before each entry,
which the dashboard parses for sorting/filtering.

### Entry format

```markdown
<!-- claude-remote-log {"date":"2026-06-28T14:32Z","session":"Refactor auth","branch":"main","claudeSessionId":"<uuid>","blockers":0,"openItems":1} -->
## 2026-06-28 · Refactor auth · main
**Done:** Added Tailscale whois caching — finished plan step 3.
**Changed:** src/server/auth/tailscale.ts, src/server/db/queries.ts
**Plan progress:** ✅ Step 3 (whois caching) ⬜ Step 4 (cache invalidation)
**Open / next:** Invalidation on logout not handled.
**Blockers:** none
```

- Newest entry on top.
- `claudeSessionId` in the marker is the idempotency key (prevents duplicates).
- If the file doesn't exist, the generator creates it with a short header.

## 3. Triggers — when an entry is generated

All triggers converge on one helper, `maybeLogSession(id)`, so behavior is
identical regardless of how a session ended.

| Case | Path in code | Logged? |
|---|---|---|
| Click terminate / header close | `terminateSession()` (`manager.ts:240`) | ✅ immediately |
| `claude`/shell exits (typed `exit`, Claude quit) | `handleSessionExit()` (`manager.ts:448`) | ✅ immediately |
| Closed browser, walked away | idle checker → `terminateSession()` (`manager.ts:101`) | ✅ after idle timeout |
| Closed browser, reconnect later | `handleDisconnect()` only (`handler.ts:585`) | ❌ session still alive (correct) |
| Graceful server shutdown | marked `idle`, not terminated (`manager.ts:628`) | ❌ resumes on restart |
| **OS shutdown / crash while session open** | server killed before any handler runs | ✅ **startup reconciliation sweep** |

### Startup reconciliation sweep (covers shutdown/crash)

Mirrors the existing `cleanupOrphanedForkFiles()` (`manager.ts:683`). At boot,
any session that:

- is **not** a fork,
- has a `claudeSessionId`,
- has no `logged_at` stamp,
- and has no live PTY (true for all sessions after a restart)

…is run through the skip-gate + generator. This retroactively logs sessions that
ended because the machine shut down or the server crashed.

### Idempotency

A new `logged_at` column on the `sessions` table (added via a numbered migration
in `schema.ts`, following the `claude_session_id` / `sort_order` precedent).
`maybeLogSession` stamps it on success; the sweep only picks up un-stamped rows.
No double-logging across clean-close, crash, and shutdown.

---

## 4. Skip-gate (avoid noise)

The gate is driven by **evidence of actual change**, not conversation length, so
Q&A / exploration sessions are ignored. Before spawning a (relatively expensive)
`claude -p` run, `maybeLogSession` evaluates, in order:

1. **Did the session edit files?** Scan the transcript JSONL for any `Edit` /
   `Write` / `MultiEdit` / `NotebookEdit` tool calls — the strongest "real work"
   signal. (Creating/updating a plan or design `.md` counts here, by design.)
2. **Did anything land in git?** `git status --porcelain` (uncommitted *and*
   untracked/new files) plus `git log` since the session's `createdAt` (commits
   made during the session).
3. **Turn-count floor** (`minTurnsToLog`) — secondary tiebreaker only.

Decision:

- **Any of (1) or (2) positive → generate an entry.**
- **None positive → skip** (a pure question/exploration session). Still stamp
  `logged_at` so the startup sweep won't retry it.

Notes:

- **Commands-only** sessions (ran tests, `git status`, `Read`/`Grep` exploration)
  with no edits and no commits are skipped, same as Q&A.
- **Non-git projects** lose signal (2), so the gate falls back to edit tool-calls
  alone. Lower fidelity (no diff ground truth) but functional — known limitation.

## 5. Generator

New module `src/server/sessions/project-log.ts`.

1. Locate the transcript with the existing `findClaudeProjectDir()`
   (`manager.ts:34`) → `<projectDir>/<claudeSessionId>.jsonl`.
2. Pre-compute `git diff` + `git log --since=<session start>` (size-bounded) for
   ground truth.
3. Spawn detached:
   ```
   claude -p "<prompt>" --output-format json
   ```
   with:
   - `cwd` = the project directory,
   - `--permission-mode acceptEdits`,
   - `allowedTools` limited to `Read`, `Edit`, `Write`, with edits **scoped to the
     log file + plan globs only** (no other files mutated).
4. The prompt instructs Claude to: read its own transcript + the provided diff +
   `CLAUDE.md` + plan files, then (a) prepend an entry to `SESSION-LOG.md`, and
   (b) tick completed checkboxes in the plan files.
5. A queue enforces `maxConcurrent`; a `timeoutMs` kills runaway runs. Fully
   detached — session teardown never blocks on generation.
6. Success/failure logged to `~/.claude-remote/logs/server.log`. Failure is
   non-fatal.

---

## 6. Plan-file matching (edit mode)

- Plan files identified by configurable globs (default `*plan*.md`, `*design*.md`,
  `docs/**/*.md`).
- The generator ticks completed checkboxes (`- [ ]` → `- [x]`) for objectives it
  judges done from the diff/transcript.
- Edits are constrained to the log file + matched plan files. Git is the safety net.

---

## 7. Configuration & modularity

Single config block (`~/.claude-remote/config.json`), feature **off by default**:

```jsonc
"projectLog": {
  "enabled": false,            // master toggle
  "fileName": "SESSION-LOG.md",
  "editPlanFiles": true,
  "planGlobs": ["*plan*.md", "*design*.md", "docs/**/*.md"],
  "maxConcurrent": 1,
  "timeoutMs": 180000,
  "minTurnsToLog": 2
}
```

When `enabled` is false, `maybeLogSession` and the startup sweep are no-ops — the
feature is fully inert, no behavioral change anywhere.

## 8. Global Claude configuration

**Decision: seed on first session-close.** New projects get their
`SESSION-LOG.md` created by the server the first time a session there closes —
only for projects you actually use. No eager per-project bootstrapping, no
auto-creation in throwaway/other repos.

The only global change is a **short, read-only convention note** in
`~/.claude/CLAUDE.md` so interactive sessions understand the file and never
clobber it. Kept minimal because global CLAUDE.md is injected into every session
for every project:

```markdown
## Session Logs (claude-remote)
Projects may keep a `SESSION-LOG.md` at the repo root — a reverse-chronological
changelog of what each work session accomplished. If one exists, read it to
understand prior work; never rewrite or reorder existing entries. claude-remote
auto-generates a new entry when a session closes, so you normally don't write it
by hand. Only create/seed `SESSION-LOG.md` if the user explicitly asks.
```

The existing `claude-session` registration hook (already required for Fork) is
reused to obtain `claudeSessionId`. No new hooks are required.

## 9. Backfilling existing projects

Discovery sources (unified):

- distinct `cwd` values from the sessions DB (projects opened in claude-remote),
- decoded `~/.claude/projects/*` directories (every Claude Code project on disk;
  each transcript JSONL line carries a `cwd` field to recover the real path).

For each discovered project without a `SESSION-LOG.md`, an on-demand backfill runs
the generator to seed **one whole-history "state of the project" entry** that
collapses all past sessions into a single "where this project stands now" summary.
Per-session entries then accrue normally going forward. Exposed as:

- `POST /api/project-logs/backfill` (all / selected projects), and
- a per-project **Generate log** button in the dashboard.

Backfilling many projects = many headless runs, so it is **on-demand**, queued,
and progress-reported — never automatic on startup.

---

## 10. Dashboard (cross-project state view)

- `GET /api/project-logs` → enumerate discovered projects, read each
  `SESSION-LOG.md`, parse the `<!-- claude-remote-log … -->` markers, return
  sorted by recency with blocker/open-item counts.
- Client: a **second tab in the existing sidebar** (alongside the sessions list),
  one click from sessions and consistent with the current single-pane layout. The
  board is sortable by staleness, filterable by "has blockers" / "has open items",
  and renders each entry's markdown prose. Projects with no log show
  "no log yet — [Generate]". Clicking a project can start/resume a session in its
  `cwd` (reusing the recent-paths machinery).
- Cost-free to render: every entry was generated once, at close time.

## 11. Edge cases

- **Fork sessions:** skipped (ephemeral by design).
- **Non-git projects:** degraded-but-working (transcript-only signal).
- **Concurrent closes:** queued via `maxConcurrent`.
- **Generation failure:** non-fatal, logged; `logged_at` left unset so the next
  startup sweep can retry.
- **Re-opened project:** next close appends the next delta entry → natural changelog.
- **Working-tree diff is not session-scoped:** the skip-gate/generator use the
  full `git diff` of the working tree, while `git log --since=<createdAt>` is
  time-bounded. So uncommitted changes that pre-date the session are attributed
  to it. Fine for the common "work, then close" flow; if it matters, snapshot
  HEAD + working-tree state at session start and diff against that, or lean on
  the transcript's edit list. (Confirmed via the step-2 smoke test.)
